# 第二轮 Step 4 模型接入边界补充

更新时间：2026-03-22

## 1. 本次收口目标

本次不开发 `model_strategy` 内部实现，只收口“前后端如何面对外部模型服务依赖”的边界表现。

## 2. 当前已确认的真实结论

- 真实可用的模型服务地址是 `http://43.153.41.145:8081/api`
- `纯文本任务链` 已经可以从前端走到后端，再走到模型服务，并进入 `processing`
- `模型服务联通` 不等于 `本地附件/本地模板链路闭环`
- 当后端仍然跑在本地且 `FILE_BASE_URL=http://127.0.0.1:8080` 时，远端模型服务仍然无法读取本机文件

## 3. 本次后端收口结果

后端现在把模型相关失败固定成几类更明确的语义：

- `模型服务未配置，请检查 MODEL_SERVICE_APP_ID 与 MODEL_SERVICE_SECRET。`
- `当前附件或模板地址仅本机可访问，远程模型服务无法读取。请检查 FILE_BASE_URL，改成模型服务可访问的公网地址，或先用纯文本任务测试。`
- `模型服务暂时不可用，请检查 MODEL_SERVICE_BASE_URL 是否正确，或稍后重试。`
- `模型服务状态查询失败，请稍后重试。`

这样做的目的，是让使用者可以直接分辨：

- 这是后端配置问题
- 这是文件访问边界问题
- 这是模型服务暂时不可用
- 还是本地业务数据本身有问题

## 4. 本次前端收口结果

前端工作台现在不再只展示一条生硬的原始错误，而是会把任务失败解释成：

- 配置问题
- 文件访问问题
- 同步问题
- 服务问题
- 业务问题

同时每类失败都会给出“下一步怎么做”的建议，例如：

- 去检查 `MODEL_SERVICE_BASE_URL / MODEL_SERVICE_APP_ID / MODEL_SERVICE_SECRET`
- 去检查 `FILE_BASE_URL`
- 先用纯文本任务验证链路
- 记录 `taskId` 并查看后端日志

## 5. 前端请求层补充

本次还补了一层很关键的请求处理：

- 任务状态接口在失败时，如果后端仍然返回了 `data`
- 前端现在会把这部分 payload 保留下来
- 不会再只剩一个异常 message，导致失败任务详情直接丢失

这意味着：

- `GET /tasks/{taskId}` 返回失败任务时
- 前端仍然可以拿到 `status / errorMessage / taskId`
- 从而把失败原因稳定地展示在主舞台里

## 6. 当前仍保留的边界

当前已经具备：

- 文本任务的模型联通演示能力

当前仍未天然具备：

- 带本地附件的远程模型读取能力
- 带本地模板文件的完整公网访问能力

如果后续要把“上传附件/模板 -> 模型服务读取 -> 最终生成结果”完整做成可演示闭环，下一步要处理的是：

- 把 `FILE_BASE_URL` 改成模型服务可以访问的公网地址
- 或者把后端/文件服务部署到模型服务可访问的环境中
