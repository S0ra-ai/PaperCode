# 附件能力研发任务拆分版（2026-03-25）

## 一、目标与执行原则

本轮不是在旧“会话附件池”方案上继续叠加功能，而是一次完整的基线切换：

- 运行时只保留“任务级附件快照”
- 不再保留、恢复、维护任何“会话附件池”
- 附件规则固定为：仅当前会话上传、仅同会话可用、仅当日可用
- 历史任务只依赖 `generate_task_files` 快照回看
- 老会话当前挂载附件一次性迁移清空
- 增加“一键复用上一轮附件”能力，但仅限当前会话最近一轮且附件仍有效

本轮验收口径不是“功能能跑”，而是“旧链路下线 + 新链路跑通 + 残留归零”。

## 二、Owner 划分

### 2.1 数据库 Owner

#### 交付目标

- 为新附件规则提供可落库的数据结构
- 清空旧 `session_files` 数据残留
- 为后端切换保留最小回滚窗口

#### 本轮必做

1. 新增迁移脚本，为 `files` 表增加以下字段：
   - `sourceSessionId`
   - `availableUntil`
2. 为 `files` 表增加索引：
   - 推荐 `(userId, sourceSessionId, availableUntil)`
3. 新增前向迁移，执行：
   - `DELETE FROM session_files`
4. 保持 `generate_task_files` 不变：
   - 历史任务快照继续依赖 `fileNameSnapshot`
5. 明确本轮采用“两段式迁移”：
   - 第一段：加字段、建索引、清空旧数据
   - 第二段：待新代码稳定后再物理删除 `session_files`

#### 本轮不做

- 不做历史 `files` 全量回填
- 不做物理文件自动清理
- 不动 `generate_task_files` 结构

#### 依赖与协作

- 需要和后端 Owner 对齐 `availableUntil` 的业务语义
- 需要和 PM 对齐业务时区口径

#### 完成定义

- `session_files` 数据为 0
- 新上传附件能写入 `sourceSessionId`
- 新上传附件能写入 `availableUntil`
- 历史任务查询不受影响

#### 下一阶段预留

- 稳定一个发布周期后执行：
  - `DROP TABLE session_files`

---

### 2.2 后端 Owner

#### 交付目标

- 去掉“会话附件池”整条后端链路
- 把任务创建校验切到“同用户 + 同会话 + 同自然日”
- 保留任务级快照作为唯一历史来源

#### 本轮必做

1. 下线旧接口：
   - `PUT /sessions/{sessionId}/attachments`
2. 删除旧服务逻辑：
   - `SessionService.updateSessionAttachments()`
   - `SessionService.replaceSessionAttachments()`
   - `SessionService.loadSessionAttachmentSnapshots()`
3. 删除工作台响应中的旧字段：
   - `attachedFiles`
   - `attachedFilesCount`
4. 删除 `TaskService` 中对 `ResearchSessionFileRepository` 的依赖
5. 删除任务创建时“未挂载到当前会话”的旧校验
6. 新增任务创建校验规则：
   - 文件属于当前用户
   - 文件 `sourceSessionId == 当前 sessionId`
   - 当前时间 `<= availableUntil`
   - 文件记录存在
7. 保留现有任务快照主链路：
   - 先落 `generate_tasks`
   - 再落 `generate_task_files`
   - 再调用模型服务
8. 新增“会话内上传附件”接口
9. 新增“查询当前会话今日可用附件”接口
10. 删除文件逻辑中移除旧保护：
   - 去掉“已挂载到会话附件池，无法删除”
11. 删除会话和管理员强删会话时，补齐新的临时附件清理行为
12. 最终删除旧模型依赖：
   - `ResearchSessionFile`
   - `ResearchSessionFileId`
   - `ResearchSessionFileRepository`

#### 本轮不做

- 不做自动过期清理任务
- 不做物理文件批量回收
- 不做模型真实读取确认

#### 依赖与协作

- 依赖数据库新增 `sourceSessionId`
- 依赖数据库新增 `availableUntil`
- 需要给前端提供新的 workspace/session-scoped 附件接口
- 需要和前端对齐“一键复用上一轮附件”的失效返回口径

#### 完成定义

- 创建任务时不再读取 `session_files`
- 工作台接口不再返回 `attachedFiles`
- 同会话同日附件可提交
- 跨会话附件被拒绝
- 次日失效附件被拒绝
- 失败任务仍保留快照
- 删除文件时不再报“会话附件池”相关错误

### 2.3 前端 Owner

#### 交付目标

- 删掉会话附件池前端链路
- 建立“当前草稿附件区”闭环
- 补齐“一键复用上一轮附件”
- 清理旧测试和旧文案

#### 本轮必做

1. 删除 API 依赖：
   - 不再调用 `updateSessionAttachments`
2. 删除状态链路：
   - 删掉 `syncSessionAttachmentPool()`
   - 删掉 `toggleFileSelection()` 中同步服务端会话附件池的逻辑
3. 删除恢复逻辑：
   - `applySessionWorkspace()` 不再根据 `workspace.attachedFiles` 恢复草稿附件
4. 删除旧工具与测试：
   - 删除 `session-attachments.js`
   - 删除 `session-attachments.test.js`
5. 把“当前选中附件”重定义为“当前草稿附件态”
6. 工作台上传改成“上传到当前草稿”
7. 保留并强化“当前草稿附件区”：
   - 显示数量
   - 显示文件名
   - 支持移除
   - 支持提交前提示
8. 改造附件列表区：
   - 改成“当前会话今日可用附件”
   - 按钮改为“加入草稿/移出草稿”
9. 提交成功后清空草稿附件区
10. 新增“一键复用上一轮附件”按钮
11. 一键复用失效处理：
   - 附件失效时按钮置灰或提示“请重新上传”
12. 替换所有旧文案：
   - “已挂载到当前会话”
   - “可自由挂载到当前会话”
   - “当前未挂载附件文献”
13. 重写相关测试：
   - `WorkspaceView.test.js`
   - `WorkspaceChatConsole.test.js`
   - `attachment-feedback-flow.test.js`

#### 本轮不做

- 不做自动恢复草稿附件
- 不做跨会话附件库
- 不做长期附件管理能力

#### 依赖与协作

- 依赖后端新建“会话内上传附件”接口
- 依赖后端新建“当前会话今日可用附件”接口
- 依赖后端工作台响应删除 `attachedFiles`
- 依赖后端返回附件有效期语义，用于前端禁用态和提示文案

#### 完成定义

- 打开老会话时，草稿附件为空
- 历史任务快照可正常显示
- 上传附件后直接进入草稿区
- 提交成功后草稿区清空
- 刷新和新浏览器不恢复草稿附件
- 同会话同日“一键复用上一轮附件”可用
- 跨会话/跨天复用不可用

## 四、推荐执行顺序

### 阶段 A：数据库先行

1. 数据库 Owner 发第一段 migration
2. 完成 `files` 新字段与索引
3. 清空 `session_files`

### 阶段 B：后端切换

1. 落新附件可用性模型
2. 切任务创建校验
3. 新增会话内上传和会话内附件列表接口
4. 工作台响应删除 `attachedFiles`
5. 下线 `updateSessionAttachments`
6. 收口删除文件、删除会话、管理员强删会话

### 阶段 C：前端切换

1. 删除旧 API/状态链路
2. 接新上传接口和新附件列表接口
3. 完成当前草稿附件区闭环
4. 提交成功后清空草稿
5. 补“一键复用上一轮附件”
6. 重写测试

### 阶段 D：联调与残留归零

1. 联调同会话同日上传、提交、回看
2. 联调跨会话复用拒绝
3. 联调跨天复用拒绝
4. 联调老会话打开后草稿为空、历史快照可看
5. 做全文残留检索

### 阶段 E：稳定后收尾

1. 观察一个发布周期
2. 第二段 migration 物理删除 `session_files`

## 九、结论

本轮如果严格按这份执行单推进，可以把上一轮遗留的数据库、后端、前端逻辑一起清掉，而不是在旧基线上继续叠补丁。

若只做“功能新增”而不做“残留归零”，后续会继续被以下旧链路拖住：

- `session_files`
- `attachedFiles`
- `updateSessionAttachments`
- “挂载到当前会话”心智

因此本轮必须以“基线切换 + 残留清理”作为同一件事推进。
