# 会话卡片预览与一次性模板改造总结

- 文档日期：2026-03-28
- 任务类型：前后端联动功能改造 + 旧业务清理 + 联调回归
- 涉及模块：`intelligen-frontend`、`intelligen-backend`

## 1. 背景与目标

本次迭代的核心目标有两条：

1. 优化会话中的任务展示方式。
   用户在会话中发起“生成报告”任务后，不再直接在聊天流里展示整段报告内容，而是改成：
   - 用户侧消息展示为“任务消息卡片”
   - 消息中带出“本次模板”和“本次附件”的文件卡片
   - AI 侧展示为“报告卡片”
   - 点击卡片后，在右侧打开大预览面板

2. 调整模板业务模型。
   原本系统里存在“模板资产 / 模板管理 / 持久化模板”这条业务链。后续需求确认后，改为：
   - 模板不再作为平台长期资产管理
   - 用户每次发起任务时临时上传一次性模板
   - 模板只服务于当前任务
   - 旧模板资产逻辑、前端管理页、接口、数据库依赖一并移除

简而言之，这次改造的最终目标是把“模板”从一个后台资产，改造成“任务提交时的一次性输入”，同时让会话界面更接近真实工作流，支持卡片式查看和右侧预览。

## 2. 本次实际完成内容

### 2.1 会话消息形态改造

前端已完成聊天区域的展示改造：

- 用户发起任务后，聊天流中展示任务消息卡片，而不是只保留纯文本输入
- 如果本次任务带了模板文件，会在消息卡片中显示“本次模板”卡片
- 如果本次任务带了附件文件，会在消息卡片中显示“附件”卡片
- AI 返回内容改为“报告卡片”，不再把整篇报告直接内联塞入聊天流
- 报告卡片中保留右侧预览入口和下载入口

这一部分的核心文件包括：

- `intelligen-frontend/src/components/workspace/WorkspaceChatConsole.vue`
- `intelligen-frontend/src/components/workspace/WorkspaceFileCard.vue`

### 2.2 右侧预览面板能力接通

已新增统一的右侧预览面板组件，用于承接以下预览入口：

- 点击“本次模板”卡片
- 点击“附件”卡片
- 点击“报告卡片”

当前预览能力如下：

- 报告：
  - 已完成任务时，优先拉取当前任务的 DOCX 并做浏览器内版式预览
  - 如果 DOCX 预览失败，则降级为格式化内容预览
  - 支持从预览面板直接下载 `DOCX` 和 `MD`
- 文件：
  - `pdf`：内嵌预览
  - 图片：直接显示图片预览
  - 文本类：加载文本后展示
  - `docx`：浏览器端实时渲染
  - 其他类型：给出“暂不支持在线预览”的降级提示

核心文件：

- `intelligen-frontend/src/components/workspace/WorkspacePreviewPanel.vue`

### 2.3 一次性模板上传链路改造

前端任务提交流程已经从“会话级模板 / 资产级模板”切换到“任务级一次性模板”：

- 用户在当前会话的发送区临时选择模板
- 提交任务时先上传该模板文件
- 上传成功后，使用返回的 `templateFileId` 提交任务
- 任务快照里记录本次模板的文件信息，用于会话卡片回显和后续预览

本次联调里还把边界处理补完整了：

- 模板上传失败时：
  - 不会误创建失败任务卡片
  - 不会产生假的任务时间线占位
  - 前端直接提示上传失败
- 模板上传成功，但任务提交失败时：
  - 会清理刚刚上传的临时模板文件
  - 避免留下孤儿文件记录

核心文件：

- `intelligen-frontend/src/views/WorkspaceView.vue`
- `intelligen-frontend/src/api/file.js`

## 3. 这次联调中重点补掉的问题

本次不是只做“功能能跑”，还顺手补了几类容易在联调中暴露的问题。

### 3.1 模板上传失败导致脏任务卡片

早期改造阶段，一个明显风险是：

- 用户点“发送任务”
- 模板上传失败
- 聊天时间线里却已经出现了一条失败任务占位

这会让用户误以为任务已经进系统，只是执行失败。实际上正确行为应该是“任务根本还没有创建成功”。

现在已经修正为：

- 模板上传成功后，才会把任务挂进时间线
- 模板上传失败时，只提示错误，不生成脏卡片

### 3.2 临时模板文件孤儿化

另一个风险是：

- 模板上传成功
- 提交任务失败
- 模板文件元数据却已经存下来了

如果不处理，会产生孤儿文件。

现在已经补上：

- 提交任务失败且任务尚未真正建立时，前端会尝试删除刚上传的临时模板文件
- 删除会话时，后端也会统一回收该会话任务关联的一次性模板文件

### 3.3 DOCX 预览脚本失败后的重试

右侧 DOCX 预览依赖浏览器运行时加载 `docx-preview`。

联调里补了一个重要兜底：

- 如果第一次脚本加载失败
- 后续再次打开预览时不会直接挂死
- 组件会正确进入失败态或触发重试逻辑

这保证了预览面板在不稳定网络环境下不会因为一次失败永久不可用。

### 3.4 空态按钮与无效点击

对一些“点了其实没意义”的交互做了限制：

- 没有真实 `taskId` 的报告占位不允许打开右侧报告预览
- 没有 `fileId` 的文件卡片不允许触发文件详情预览

这样可以减少联调时用户感受到的“点了没反应”问题。

## 5. 当前已知限制

以下是本次交付后仍然存在，但不阻塞使用的点：

### 5.1 DOCX 在线预览依赖 CDN

当前 `docx-preview` 是在浏览器运行时通过 CDN 加载。

影响：

- 如果部署环境无法访问 jsDelivr
- 右侧 DOCX 在线预览会失败

当前兜底：

- 报告会降级为格式化内容预览
- 不会导致整个页面卡死

### 5.2 包体仍有 warning

前端构建仍会提示单个 chunk 偏大。

当前结论：

- 只是构建 warning
- 不影响这次功能使用
- 后续如要继续优化，可单独做代码分包

从用户视角看，这次改造后系统行为已经变成：

1. 用户在聊天区输入任务内容
2. 用户临时选择“本次模板”
3. 用户选择“本次附件”
4. 发送后，聊天流里出现一条任务消息卡片
5. 卡片内展示本次模板和附件
6. AI 返回报告卡片，而不是整篇报告文本
7. 点击模板、附件或报告卡片，在右侧打开大预览面板

这已经符合本轮需求的核心目标。

## 7. 建议的后续工作

如果继续往下优化，建议优先做下面三项：

1. 浏览器实机走查
   重点看桌面端、窄屏、滚动区域和右侧预览宽度是否足够自然。

2. 视觉微调
   重点调卡片文案、按钮状态、预览空态提示、模板与附件标签区分度。

3. 本地化 DOCX 预览依赖
   如果后续要提高稳定性，建议把 `docx-preview` 从 CDN 运行时依赖改成项目内依赖或本地静态资源。
