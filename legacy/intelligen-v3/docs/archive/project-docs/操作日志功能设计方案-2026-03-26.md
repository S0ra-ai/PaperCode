# 操作日志（管理员全量留痕，双层日志）功能设计方案

> 文档日期：2026-03-26  
> 适用项目：IntelliGen  
> 技术栈：Spring Boot 3.5 · JPA · MySQL · Flyway · Vue 3

---

## 一、目标与范围

### 1. 目标

本方案满足以下两个目标：

- **管理员账号发起的所有可执行操作都要留痕**
- **避免高频查询、自动轮询把主审计表冲成噪音大表**

因此，本方案采用**双层日志**设计，而不是把所有管理员请求都写进同一张永久保留的审计表。

### 2. 留痕边界

- 是否记录，首先看**操作者是否为管理员**
- 只要当前登录用户具备 `ROLE_ADMIN`，其请求必须进入某一层日志
- 普通用户发起的同路径请求**不记录**
- 匿名接口和公共接口默认**不记录**，例如 `/api/health`、`/auth/register`
- 管理员登录成功应记录
- 管理员登录失败仅在“用户名命中管理员账号”时记录；未命中管理员账号的失败尝试不写入本方案日志

### 3. 分层策略

#### 主审计日志 `operation_logs`

记录**关键、敏感、可追责**的管理员行为，特点如下：

- 默认长期保留
- 用于日常审计、追责、问题回溯
- 以状态变化操作为主
- 补充少量高价值读取行为，例如报告下载

#### 访问留痕日志 `admin_access_logs`

记录**非关键但仍需留痕**的管理员访问行为，特点如下：

- 记录查询、列表、详情查看、工作区刷新、任务轮询等行为
- 与主审计日志分表存储
- 默认保留 90 天，可配置
- 默认不在“关键审计”主视图展示，避免淹没真正重要的审计事件

### 4. 特别说明

- “管理员查看审计日志”本身仍要留痕，但写入 `admin_access_logs`，不写入 `operation_logs`
- 自动轮询与自动刷新也要留痕，但归入 `admin_access_logs`
- 本方案不再使用“只审计 `/admin/**`”作为边界，而是改为“按操作者角色 + 操作类型”判定

## 二、事件分层设计

### 1. 写入 `operation_logs` 的关键审计事件

| 操作码 | 描述 | 方法与路径 |
|---|---|---|
| `ADMIN_LOGIN_SUCCESS` | 管理员登录成功 | `POST /auth/login` |
| `ADMIN_LOGIN_FAILURE` | 管理员登录失败（仅限可识别为管理员账号） | `POST /auth/login` |
| `ADMIN_UPDATE_PROFILE` | 修改管理员个人资料 | `PUT /auth/profile` |
| `ADMIN_UPDATE_PASSWORD` | 修改管理员密码 | `PUT /auth/password` |
| `ADMIN_CREATE_SESSION` | 创建会话 | `POST /sessions` |
| `ADMIN_DELETE_SESSION` | 删除自己的会话 | `DELETE /sessions/{sessionId}` |
| `ADMIN_UPLOAD_SESSION_ATTACHMENT` | 上传会话附件文献 | `POST /sessions/{sessionId}/attachments` |
| `ADMIN_CREATE_TASK` | 提交生成任务 | `POST /sessions/{sessionId}/tasks` |
| `ADMIN_DOWNLOAD_TASK_REPORT` | 下载报告 | `GET /tasks/{taskId}/download` |
| `ADMIN_UPLOAD_FILE` | 上传个人文件 | `POST /files/upload` |
| `ADMIN_DELETE_FILE` | 删除个人文件 | `DELETE /files/{fileId}` |
| `ADMIN_CREATE_TEMPLATE` | 创建模板 | `POST /admin/templates` |
| `ADMIN_DELETE_TEMPLATE` | 删除模板 | `DELETE /admin/templates/{templateId}` |
| `ADMIN_AUDIT_USER` | 审核用户（通过/驳回） | `PUT /admin/users/{userId}/audit` |
| `ADMIN_FORCE_DELETE_SESSION` | 后台强制清理会话及其关联任务记录 | `DELETE /admin/sessions/{sessionId}` |

说明：

- 这里以“状态变化、敏感操作、导出操作”为主
- 即使是 `GET /tasks/{taskId}/download`，因为属于导出行为，仍进入主审计日志
- 主审计日志不记录普通列表查询、详情查看、轮询刷新

### 2. 写入 `admin_access_logs` 的访问留痕事件

| 操作码 | 描述 | 方法与路径 |
|---|---|---|
| `ADMIN_GET_USERINFO` | 获取当前管理员信息 | `GET /auth/userinfo` |
| `ADMIN_LIST_SESSIONS` | 查看会话列表 | `GET /sessions` |
| `ADMIN_VIEW_SESSION_DETAIL` | 查看会话详情 | `GET /sessions/{sessionId}` |
| `ADMIN_VIEW_SESSION_WORKSPACE` | 查看会话工作区 | `GET /sessions/{sessionId}/workspace` |
| `ADMIN_LIST_SESSION_ATTACHMENTS` | 查看会话附件列表 | `GET /sessions/{sessionId}/attachments` |
| `ADMIN_LIST_SESSION_TASKS` | 查看会话任务列表 | `GET /sessions/{sessionId}/tasks` |
| `ADMIN_VIEW_TASK_STATUS` | 查看任务状态 | `GET /tasks/{taskId}` |
| `ADMIN_LIST_FILES` | 查看个人文件列表 | `GET /files` |
| `ADMIN_VIEW_FILE_DETAIL` | 查看文件详情 | `GET /files/{fileId}` |
| `ADMIN_LIST_TEMPLATES` | 查看模板列表 | `GET /templates` |
| `ADMIN_LIST_PENDING_USERS` | 查看待审核用户列表 | `GET /admin/users/pending` |
| `ADMIN_VIEW_AUDIT_LOGS` | 查看审计日志 | `GET /admin/audit-logs` |
| `ADMIN_VIEW_ACCESS_LOGS` | 查看访问留痕日志 | `GET /admin/access-logs` |

说明：

- 这些操作仍然要留痕，但不进入主审计表
- 自动刷新、静默预加载、轮询产生的访问记录统一进入该表
- 审计日志页本身产生的访问行为也只写入该表，避免污染主审计结果
- `ADMIN_VIEW_AUDIT_LOGS` 与 `ADMIN_VIEW_ACCESS_LOGS` 默认在访问留痕页中隐藏，需要手动勾选后查看

### 3. 当前明确不记录的请求

- `/api/health`
- `/auth/register`
- 未认证请求
- 非管理员用户请求

## 三、数据库设计

### 1. 主审计表：`operation_logs`

**Flyway 迁移文件**：`V6__operation_logs.sql`

```sql
CREATE TABLE `operation_logs` (
    `logId`            VARCHAR(36)  NOT NULL,
    `requestId`        VARCHAR(64)  NOT NULL,    -- 服务端内部生成的单次请求关联 ID
    `upstreamRequestId` VARCHAR(128) NULL,       -- 上游透传的请求 ID，仅用于排障
    `traceId`          VARCHAR(64)  NULL,        -- 分布式链路 ID，无链路系统时可为空
    `operatorUserId`   VARCHAR(36)  NULL,        -- 登录失败时允许为空
    `operatorUsername` VARCHAR(255) NULL,        -- 用户名快照或登录尝试用户名
    `operatorRole`     VARCHAR(50)  NOT NULL,    -- 固定为 ADMIN
    `operationScope`   VARCHAR(30)  NOT NULL DEFAULT 'ADMIN_ACCOUNT',
    `action`           VARCHAR(100) NOT NULL,    -- 仅记录关键 ADMIN_* 事件
    `targetType`       VARCHAR(50)  NULL,        -- SESSION / TASK / FILE / TEMPLATE / USER / PROFILE
    `targetId`         VARCHAR(64)  NULL,
    `detail`           TEXT         NULL,        -- JSON 字符串
    `ip`               VARCHAR(45)  NULL,
    `userAgent`        VARCHAR(500) NULL,
    `requestPath`      VARCHAR(255) NOT NULL,
    `httpMethod`       VARCHAR(10)  NOT NULL,
    `status`           VARCHAR(20)  NOT NULL,    -- SUCCESS / FAILURE
    `httpStatus`       INT          NULL,
    `errorMsg`         TEXT         NULL,
    `createdAt`        DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT `pk_operation_logs` PRIMARY KEY (`logId`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE INDEX `idx_operation_logs_operatorUserId` ON `operation_logs` (`operatorUserId`);
CREATE INDEX `idx_operation_logs_requestId`      ON `operation_logs` (`requestId`);
CREATE INDEX `idx_operation_logs_traceId`        ON `operation_logs` (`traceId`);
CREATE INDEX `idx_operation_logs_action`         ON `operation_logs` (`action`);
CREATE INDEX `idx_operation_logs_createdAt`      ON `operation_logs` (`createdAt`);
CREATE INDEX `idx_operation_logs_scope`          ON `operation_logs` (`operationScope`);
```

### 2. 访问留痕表：`admin_access_logs`

**Flyway 迁移文件**：`V7__admin_access_logs.sql`

```sql
CREATE TABLE `admin_access_logs` (
    `accessLogId`      VARCHAR(36)  NOT NULL,
    `requestId`        VARCHAR(64)  NOT NULL,    -- 服务端内部生成的请求关联 ID
    `upstreamRequestId` VARCHAR(128) NULL,       -- 上游透传的请求 ID，仅用于排障
    `traceId`          VARCHAR(64)  NULL,
    `operatorUserId`   VARCHAR(36)  NOT NULL,
    `operatorUsername` VARCHAR(255) NOT NULL,
    `operatorRole`     VARCHAR(50)  NOT NULL,    -- 固定为 ADMIN
    `action`           VARCHAR(100) NOT NULL,
    `targetType`       VARCHAR(50)  NULL,
    `targetId`         VARCHAR(64)  NULL,
    `detail`           TEXT         NULL,
    `ip`               VARCHAR(45)  NULL,
    `userAgent`        VARCHAR(500) NULL,
    `requestPath`      VARCHAR(255) NOT NULL,
    `httpMethod`       VARCHAR(10)  NOT NULL,
    `triggerSource`    VARCHAR(20)  NOT NULL,    -- USER_ACTION / AUTO_REFRESH / SYSTEM_FALLBACK / UNKNOWN
    `status`           VARCHAR(20)  NOT NULL,
    `httpStatus`       INT          NULL,
    `errorMsg`         TEXT         NULL,
    `createdAt`        DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT `pk_admin_access_logs` PRIMARY KEY (`accessLogId`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE INDEX `idx_admin_access_logs_operatorUserId` ON `admin_access_logs` (`operatorUserId`);
CREATE INDEX `idx_admin_access_logs_requestId`      ON `admin_access_logs` (`requestId`);
CREATE INDEX `idx_admin_access_logs_traceId`        ON `admin_access_logs` (`traceId`);
CREATE INDEX `idx_admin_access_logs_action`         ON `admin_access_logs` (`action`);
CREATE INDEX `idx_admin_access_logs_createdAt`      ON `admin_access_logs` (`createdAt`);
CREATE INDEX `idx_admin_access_logs_triggerSource`  ON `admin_access_logs` (`triggerSource`);
```

### 3. 字段说明

- `operatorRole` 用于保留操作发生当时的管理员身份快照，避免后续角色变化影响解释
- `operationScope='ADMIN_ACCOUNT'` 表示主审计表承载的是管理员账号关键操作审计
- `requestId` 由服务端内部生成，用于把一次请求在不同日志表中的记录串联起来，便于事后还原完整时间线
- `upstreamRequestId` 保留上游透传值，仅用于与网关/CDN/客户端排障信息做关联
- `traceId` 用于与应用日志、链路追踪、网关日志进行关联
- `triggerSource` 仅出现在访问留痕表，用于区分人工访问、自动刷新和无法可靠判定的访问
- `httpStatus` 便于区分业务失败、参数错误、权限失败等结果

### 4. 保留策略

- `operation_logs`：长期保留
- `admin_access_logs`：在线热数据默认保留 90 天，可配置
- `admin_access_logs` 在线数据清理前，必须先归档到冷存储或归档表，不允许直接删除
- `admin_access_logs` 的总保留周期应与审计要求对齐，默认不少于 365 天；若项目要求更高，可与 `operation_logs` 保持同周期
- 审计页面默认只查在线热数据；历史归档数据通过离线导出或归档检索方式获取

### 5. `detail` 建议字段

主审计日志：

- 会话创建/删除：`sessionTitle`、`templateFileId`
- 附件上传：`sessionId`、`sessionTitle`、`fileId`、`fileName`
- 任务提交：`sessionId`、`sessionTitle`、`taskId`
- 报告下载：`taskId`、`sessionId`、`format`
- 文件上传/删除：`fileId`、`fileName`
- 用户审核：`targetUserId`、`auditResult`
- 强制清理会话：`sessionTitle`、`sessionOwnerUserId`、`deletedTaskCount`、`deletedTaskFileRelationCount`

访问留痕日志：

- 审计日志查询：`filters`、`page`、`pageSize`
- 工作区刷新：`sessionId`
- 任务状态轮询：`taskId`、`sessionId`

### 6. 敏感信息脱敏规则

以下字段**严禁**写入 `operation_logs`、`admin_access_logs`、应用普通日志或异步补偿载荷：

- 明文密码
- 加密后密码/密码哈希
- 新旧密码字段
- Token、JWT、Refresh Token
- `Authorization` 请求头
- Cookie、Session 标识
- 完整请求体中的认证敏感字段
- 完整异常堆栈

认证类与改密类事件的允许记录范围：

- `ADMIN_LOGIN_SUCCESS`：仅记录脱敏后的用户名、结果状态、IP、User-Agent、requestId、traceId
- `ADMIN_LOGIN_FAILURE`：仅记录脱敏后的尝试用户名、失败原因分类、IP、User-Agent、requestId、traceId
- `ADMIN_UPDATE_PASSWORD`：仅记录操作成功/失败、管理员 ID、IP、User-Agent、requestId、traceId；不得记录密码相关字段

脱敏要求：

- 用户名可按业务需要部分脱敏展示
- `errorMsg` 仅允许保存白名单化后的错误摘要，不允许直接落完整异常堆栈
- `detail` 必须按 action 做字段白名单映射，禁止直接序列化整个 request/response 对象
- 若命中敏感字段，必须在写日志前剔除，并输出脱敏命中计数指标

## 四、后端实现

### 1. 模块结构

新建包 `com.intelligen.backend.auditlog`：

```text
auditlog/
├── constant/       AuditAction.java
├── constant/       LogCategory.java          ← AUDIT / ACCESS / SKIP
├── entity/         OperationLog.java
├── entity/         AdminAccessLog.java
├── repository/     OperationLogRepository.java
├── repository/     AdminAccessLogRepository.java
├── service/        AuditLogService.java
├── interceptor/    AdminOperationAuditInterceptor.java
├── resolver/       AuditDecisionResolver.java
├── resolver/       TriggerSourceResolver.java
├── resolver/       AuditDetailResolver.java
├── dto/            OperationLogResponse.java
└── controller/     AuditLogController.java
```

### 2. 核心实现原则

1. 不再依赖“手工给每个接口加 `@Audit`”
2. 改为**全局拦截所有 Controller 请求**
3. 拦截后先判断：
   - 是否存在已认证 `Authentication`
   - 当前用户是否具备 `ROLE_ADMIN`
4. 若不满足，则直接跳过
5. 若满足，则由 `AuditDecisionResolver` 判定：
   - 写入 `operation_logs`
   - 写入 `admin_access_logs`
   - 或显式 `SKIP`
6. 请求结束后在 `afterCompletion` 统一记录最终结果
7. 登录成功/失败属于认证边界场景，仍通过 `AuthService` 手工写入主审计日志

### 2.1 `requestId` / `traceId` 生成与传播规则

- 通过统一的 Servlet Filter 生成服务端内部 `requestId`
- 如上游已传 `X-Request-Id`，仅保存到 `upstreamRequestId`，不得直接作为内部 `requestId`
- 内部 `requestId` 必须在服务端入口生成新的 UUID/雪花 ID，避免客户端或中间层污染审计关联链路
- `traceId` 如已有链路追踪系统则直接复用；没有时可为空，但 `requestId` 必须存在
- 生成后的 `requestId` / `traceId` 必须同时写入：
  - `MDC`
  - `HttpServletRequest attributes`
  - 响应头（便于前端和问题排查）
- `upstreamRequestId` 如存在，也应写入 request attributes，供审计写入器和问题排查读取
- `AdminOperationAuditInterceptor`、`AuthService` 手工审计埋点、异步写入器、补偿任务都必须从同一上下文读取 `requestId` / `traceId`
- 若异步写入或补偿在原请求线程之外执行，必须把 `requestId` / `traceId` 作为显式字段传递，不能依赖线程本地变量自动继承
- 若请求进入审计链路时缺失 `requestId`，应立即补生成并输出告警，禁止写入空值

### 3. 为什么不用单表

如果把管理员所有 GET 请求、自动刷新、轮询都写进同一张永久保留表，会产生以下问题：

- 高频请求迅速膨胀数据量
- 真正关键的创建、删除、审核、导出行为被淹没
- 审计页面查询本身不断制造新的审计记录

因此，“全量留痕”与“稳定可用”必须通过**双表分层**同时满足。

### 4. `triggerSource` 的可信规则

`triggerSource` 仅作为**辅助分类标签**，不能完全信任前端自报，也不能只靠路径硬编码。

服务端规则如下：

1. 对于“同一路径既可能是人工查看，也可能是自动轮询”的**歧义路径**，前端必须显式传递 `X-Audit-Trigger`
2. 当前已知歧义路径至少包括：
   - `GET /sessions/{sessionId}/workspace`
   - `GET /tasks/{taskId}`
   - `GET /sessions/{sessionId}/attachments`
3. 若前端传入合法值，则优先采用：
   - `USER_ACTION`
   - `AUTO_REFRESH`
   - `SYSTEM_FALLBACK`
4. 若歧义路径未传值、传入非法值或与服务端上下文冲突，则记录为 `UNKNOWN`，并输出告警指标
5. 只有在服务端能可靠识别为系统兜底流程时，才允许写成 `SYSTEM_FALLBACK`
6. 非歧义路径在未显式标记时默认记为 `USER_ACTION`

### 5. 建议的写入策略

主审计日志：

- 使用独立事务落库
- 关键操作失败也必须留痕
- 写入失败时应输出错误日志并触发监控告警

访问留痕日志：

- 不允许静默丢失
- 默认方案应保证请求先落到可恢复介质，再异步或同步写入 `admin_access_logs`
- 若采用异步批量写入，必须基于 durable outbox / 本地可重试队列，保证最终一致
- 单次消费失败不回滚业务响应，但必须进入重试、补偿和监控告警流程
- 若最终写入失败，必须保留失败记录与补偿入口，不能接受“失败即丢”

### 6. 防漏记机制

- 维护一份“Controller 方法 -> `LogCategory + AuditAction`”集中映射
- 新增可认证接口时，单元测试必须校验其已被映射或被显式排除
- 若管理员请求未解析到映射，不应静默跳过：
  - 关键写操作应按 `ADMIN_UNMAPPED_OPERATION` 写入主审计日志
  - 非关键读操作应按 `ADMIN_UNMAPPED_ACCESS` 写入访问留痕日志

### 7. 登录失败记录规则

`POST /auth/login` 的失败记录只在以下条件满足时写入主审计日志：

- 根据输入用户名查到了用户
- 该用户角色为 `ADMIN`

否则不写入本方案日志，避免把普通用户登录失败混入管理员审计。

### 8. 查询接口

关键审计日志：

```text
GET /admin/audit-logs
```

查询参数建议支持：

- `page`
- `pageSize`
- `requestId`
- `traceId`
- `action`
- `status`
- `operatorUserId`
- `httpMethod`
- `startTime`
- `endTime`

访问留痕日志：

```text
GET /admin/access-logs
```

查询参数建议支持：

- `page`
- `pageSize`
- `requestId`
- `traceId`
- `action`
- `status`
- `operatorUserId`
- `httpMethod`
- `triggerSource`
- `startTime`
- `endTime`

### 1. 页面设计

- 默认打开“关键审计”标签页
- “访问留痕”标签页单独展示列表查询、详情查看、轮询刷新等事件
- 主审计页默认不混入 `admin_access_logs`
- 访问留痕页默认隐藏 `AUTO_REFRESH`，允许用户手动打开筛选
- 访问留痕页默认隐藏 `ADMIN_VIEW_AUDIT_LOGS` 与 `ADMIN_VIEW_ACCESS_LOGS`
- 两个标签页都支持按 `requestId` / `traceId` 检索与串联

### 2. 前端配合要求

- 对歧义路径，前端必须显式传 `X-Audit-Trigger`
- 用户主动打开工作区、附件列表、任务状态时，应传 `X-Audit-Trigger: USER_ACTION`
- 自动轮询、自动刷新、静默预加载请求，应传 `X-Audit-Trigger: AUTO_REFRESH`
- 若后续有失败后的管理员兜底重试流程，可传 `X-Audit-Trigger: SYSTEM_FALLBACK`
- 若歧义路径未传该头，后端必须记为 `UNKNOWN`，而不是强行猜成 `AUTO_REFRESH`
- `api/session.js`、`api/task.js`、必要时 `api/task-download.js` 应允许调用方传入附加 headers/config
- `WorkspaceView.vue` 需明确区分首次进入、手动切换、轮询刷新三类调用场景，避免统一走默认请求
- “查看审计日志”页面请求只进入访问留痕，不应出现在主审计页

## 六、验证计划

1. 后端启动，Flyway 自动执行 `V6` 与 `V7`，确认 `operation_logs` 和 `admin_access_logs` 表创建成功
2. 普通用户登录后执行创建会话、上传附件、提交任务、下载报告，确认两张表**都没有新增记录**

4. 管理员创建会话，确认在 `operation_logs` 记录 `ADMIN_CREATE_SESSION`

6. 管理员提交生成任务，确认在 `operation_logs` 记录 `ADMIN_CREATE_TASK`
7. 管理员下载报告，确认在 `operation_logs` 记录 `ADMIN_DOWNLOAD_TASK_REPORT`
8. 管理员审核用户、创建模板、删除模板、强制清理会话，确认均写入 `operation_logs`
9. 管理员查看会话列表、会话详情、文件列表、模板列表，确认写入 `admin_access_logs`，不写入 `operation_logs`
10. 管理员手动打开 `GET /sessions/{sessionId}/workspace` 时，确认写入 `admin_access_logs`，且 `triggerSource=USER_ACTION`
11. 活动任务期间验证 `GET /sessions/{sessionId}/workspace` 每 5 秒轮询时写入 `admin_access_logs`，且 `triggerSource=AUTO_REFRESH`
12. 验证 `GET /tasks/{taskId}` 的任务状态轮询写入 `admin_access_logs`，且 `triggerSource=AUTO_REFRESH`

18. 验证 `admin_access_logs` 在线数据归档后仍可通过归档检索或导出方式获取，不发生无归档直接删除
19. 验证访问留痕在异步消费失败时进入重试/补偿流程，不发生静默丢失

## 七、结论

本方案采用“**管理员全量留痕，双层分流**”的方式实现更稳的设计：

- 管理员所有操作都有记录
- 关键操作进入主审计日志，适合长期保留和追责
- 高频查询、轮询、审计页访问进入访问留痕日志，避免主审计表失真
- 服务端对 `triggerSource` 做保守兜底判定，歧义场景宁可记为 `UNKNOWN` 也不误判
- 双表通过 `requestId` / `traceId` 串联，便于还原完整管理员操作链路
- 访问留痕采用“在线热数据 + 冷归档”的保留策略，避免容量压力与长期追溯相冲突

最终红线如下：

- 只要操作者是管理员，其请求必须进入某一层日志
- 主审计日志不得被高频读取事件污染
- 审计日志查询行为不得反向污染主审计结果
- 不能只靠路径 `/admin/**` 判定是否审计
- 不能完全信任前端传入的 `triggerSource`
- 歧义路径缺失来源标记时，必须记为 `UNKNOWN`，不能强行猜测
- 访问留痕不能静默丢失
