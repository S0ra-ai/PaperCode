# 第三轮：报告阅读与 Markdown / DOCX 导出实施计划

更新时间：2026-03-23

## 1. 目标冻结

本轮不改模型服务输出协议，继续以现有的 `resultMarkdown` 作为唯一任务结果来源。

本轮要解决的问题分为三层：

1. 前端不要再把研究结果当成 Markdown 源码直接展示。
2. 系统要具备正式的报告下载能力，面向用户的主要交付格式为 `docx + md`。
3. 后续逐步提升导出成品感，包括更稳定的分页、封面、目录、模板套版。

## 2. 固定结论

- 当前正式开发文档里的结果字段就是 `resultMarkdown`。
- `/tasks/{taskId}/download` 已在 API 文档中预留，但尚未落地。
- 网页阅读体验和导出成品是两个层级，不混为一件事。
- `md` 既作为内部中间格式，也作为用户可下载的原文格式。
- `pdf` 不纳入本轮范围。
- 真正接近 Word 成品的分页能力，优先在导出文件里实现，不追求先在网页里做伪分页。

## 3. 执行原则

- 严格按本文档顺序执行，不跳步。
- 每完成一阶段再进入下一阶段。
- 不在本轮中途改模型服务输出结构，除非用户明确要求。
- 不把网页阅读体验和文件导出能力混在一个补丁里一次性硬做。
- 如果某一步需要新增依赖、接口或文档补充，先在该阶段内完成闭环再继续下一步。

## 4. 实施范围

### 前端范围

- `intelligen-frontend/src/components/workspace/WorkspaceChatConsole.vue`
- 新增报告渲染组件
- 新增 Markdown 渲染工具与样式
- 工作台中的报告查看、切换与下载入口

### 后端范围

- `intelligen-backend/src/main/java/com/intelligen/backend/task/controller/TaskController.java`
- `intelligen-backend/src/main/java/com/intelligen/backend/task/service/TaskService.java`
- 新增报告导出相关 service / util / dto
- 视需要新增模板渲染与导出依赖

## 5. 分阶段计划

## Step 1. 前端报告阅读模式重构

### 目标

把当前原始 Markdown 文本块改成真正的报告阅读视图。

### 具体实施

- 新增独立报告组件，例如：
  - `intelligen-frontend/src/components/workspace/TaskReportViewer.vue`
- 新增 Markdown 渲染工具，例如：
  - `intelligen-frontend/src/utils/report-markdown.js`
- 引入 Markdown 解析与安全渲染能力：
  - Markdown 解析
  - HTML 安全过滤
  - 标题、列表、引用、表格、代码块样式
- 在 `WorkspaceChatConsole.vue` 中替换当前 `<pre class="result-content">`
- 增加视图切换：
  - 报告视图
  - Markdown 原文
- 增加基础交互：
  - 复制报告内容
  - 单独展开阅读

### 验收标准

- 完成任务后，用户看到的是报告页面，不是 Markdown 源码。
- 标题、正文、列表、表格、引用可正常阅读。
- 仍然可以切换查看原始 Markdown。
- `npm run test`、`npm run build` 通过。

## Step 2. 下载接口与格式契约落地

### 目标

把 API 文档里预留的 `/tasks/{taskId}/download` 正式落地，并冻结用户可见的下载格式契约。

### 具体实施

- 在 `TaskController.java` 增加：
  - `GET /tasks/{taskId}/download`
- 在 `TaskService.java` 增加下载能力入口
- 冻结接口调用方式：
  - `/tasks/{taskId}/download?format=docx`
  - `/tasks/{taskId}/download?format=md`
- 前端下载入口展示：
  - 下载 DOCX
  - 下载 Markdown
- `pdf` 不出现在用户下载入口中
- 权限校验沿用当前任务归属校验逻辑

### 验收标准

- 下载接口路径与参数形式固定
- 前端下载入口明确面向 `docx + md`
- 未完成任务不能误下载空报告
- 非本人任务不能下载
- 后端测试通过

## Step 3. DOCX 导出能力

### 目标

让系统可以导出 Word 可编辑版本，满足继续人工修改和正式交付的场景。

### 具体实施

- 在后端增加 `format=docx` 导出分支
- 在后端增加 `format=md` 下载分支
- 将 Markdown 内容映射为 Word 结构：
  - 标题层级
  - 正文段落
  - 列表
  - 表格
  - 引用
- 增强导出样式模板：
  - 封面标题
  - 正文层级
  - 表格样式
  - 页眉页脚
- 如果模板文件可用，再评估是否进入模板套版模式
- 文件名规则固定，例如：
  - `研究报告-{taskId}.docx`
  - `研究报告-{taskId}.md`

### 关键说明

- 这一阶段默认先完成结构化 DOCX
- 严格套用外部 Word 模板属于增强项，不在本阶段第一优先级
- 网页阅读页不追求完全模拟 Word 分页

### 验收标准

- 已完成任务可下载 DOCX
- 已完成任务可下载 Markdown 原文
- Word 打开无损坏
- 标题、正文、表格有基本层级
- 文档可以继续人工编辑

## Step 4. 成品化与模板套版增强

### 目标

在 DOCX 已可用的前提下，进一步提升成品感。

### 具体实施

- 增强封面、目录、页眉页脚
- 如果模板链路稳定，再评估：
  - 根据 `templateFileId` 套用导出模板
  - 不同模板输出不同报告皮肤
- 优化长报告章节分页
- 统一下载入口与状态提示

### 验收标准

- 导出文件接近正式交付件
- 模板对成品样式有可见影响
- 用户能明确区分阅读视图和导出成品

## 6. 非本轮优先事项

- 不改数据库结果字段名
- 不要求模型服务直接返回 DOCX 二进制
- 不先做网页内 Word 式精确分页预览
- 不把所有模板套版能力挤到第一阶段
- 不实现 PDF 导出

## 7. 推荐执行顺序

必须严格按以下顺序推进：

1. Step 1：前端报告阅读模式重构
2. Step 2：下载接口与格式契约落地
3. Step 3：DOCX 导出能力
4. Step 4：成品化与模板套版增强

## 8. 完成定义

只有满足以下条件，才算本轮真正完成：

- 工作台中报告已不是 Markdown 源码展示
- `/tasks/{taskId}/download` 已正式可用
- 至少支持 `docx + md` 两种用户下载交付路径
- 关键测试与构建全部通过
- 差异与补充写入项目补充文档

## 9. 执行约束

从本文件创建开始，后续默认严格按照本计划执行。

如果要变更：

- 必须由用户明确调整优先级
- 或者出现无法继续推进的技术阻塞

否则不改路线、不跳阶段、不把增强项提前到主线前面。
