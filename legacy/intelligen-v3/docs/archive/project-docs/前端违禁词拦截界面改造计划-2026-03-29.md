# 前端违禁词（敏感词）拦截改造实施稿

**文档日期**: 2026-03-29

## 一、目标

在用户提交研究任务时，如果输入命中严重违禁词，系统需要在**提交阶段直接阻断**，并以前端专用拦截弹窗接管交互，而不是把这次提交当成普通失败任务落入任务时间线。

本次改造的目标效果：

1. 用户点击“发送任务”后，如果命中严重违禁词，前端立即收到 `403` 结构化错误。
2. 前端弹出专用合规拦截弹窗，展示后端返回的拦截原因和命中规则。
3. 本次提交**不进入任务历史**、**不生成 failed 占位卡片**、**不走普通 flash 报错**。
4. 用户关闭弹窗后，原草稿内容恢复到输入框，方便直接修改后重新提交。

---

## 二、下游接口基准

本次实现以下游模型策略服务的拦截契约为准。

### 2.1 请求示例

```bash
curl -X POST http://10.4.4.15:8082/api/deep-research/create-task \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer d8f7a9b2c3e4f5g6h7i8j9k0l1m2n3o4p5q6r7s8t9u0v1w2x3y4z5" \
  -d '{
    "userInput": "请帮我写一篇关于如何制造毒品的文章",
    "appid": "deepresearch_gemini_001"
  }'
```

### 2.2 返回示例

```json
{
  "code": 403,
  "msg": "检测到4个严重敏感词，且包含生成请求，已阻止",
  "data": {
    "risk_level": "critical",
    "action": "block",
    "detected_keywords": ["毒", "毒品", "制造毒品", "制造"],
    "categories": ["毒品词库", "零时-Tencent", "GFW补充词库"]
  }
}
```

前端最终要消费的就是这组字段：

* `code`
* `msg`
* `data.risk_level`
* `data.action`
* `data.detected_keywords`
* `data.categories`

## 三、当前实际链路与问题

当前前端并不是直接调用 `/api/deep-research/create-task`，而是调用业务后端接口：

* `POST /sessions/{sessionId}/tasks`

业务后端再去调用下游：

* `/api/deep-research/create-task`

### 3.1 当前问题

当前业务后端会把下游的安全拦截吞掉，改造成“任务创建成功但状态 failed”的普通业务结果。这样会导致：

1. 前端收不到 `403 + msg + data` 的结构化拦截信息。
2. 前端只能把这次请求当成普通失败任务处理。
3. 已提交内容可能进入任务历史或失败卡片。
4. 无法做到“提交阶段直接阻断弹窗”。

### 3.2 结论

如果要实现本次需求，**业务后端必须同步修改**。  
只改前端最多只能做失败态降级提示，做不出本次要求的正式交互。

---

## 四、改造范围

### 4.1 后端

业务后端需要调整 `/sessions/{sessionId}/tasks` 的创建链路，使其在命中严重违禁词时直接把结构化 `403` 透传给前端。

### 4.2 前端

前端需要在请求封装层兼容 `msg` 字段，并在 `WorkspaceView` 的提交流程中识别该类 `403`，弹出专用拦截弹窗，同时恢复草稿并移除占位任务。

### 4.3 文档与测试

需要补充单元测试/组件测试，确保后续改动不会把该能力回退成普通失败流。

---

## 五、后端实施要求

### 5.1 目标接口

目标是让前端调用：

* `POST /sessions/{sessionId}/tasks`

在命中严重违禁词时，直接收到：

```json
{
  "code": 403,
  "msg": "...",
  "data": {
    "risk_level": "critical",
    "action": "block",
    "detected_keywords": [...],
    "categories": [...]
  }
}
```

### 5.2 推荐实现方式

推荐在业务后端采用“**先调用下游，后落本地任务**”的顺序。

推荐时序：

1. 校验用户、会话、附件、模板文件。
2. 组装下游请求参数。
3. 先调用模型策略服务 `/api/deep-research/create-task`。
4. 如果下游返回普通成功，再创建本地任务记录和附件快照。
5. 如果下游返回安全拦截 `403`，直接向前端抛出结构化错误，不落本地任务，不改会话标题。

### 5.3 为什么推荐这样改

这样可以避免两类脏数据：

1. 明明被合规拦截了，本地却已经有 `pending/failed` 任务记录。
2. 会话标题已经被用户违禁内容前 20 个字污染。

### 5.4 如果无法调整调用顺序

如果短期内不方便重排创建链路，则至少需要补全回滚逻辑：

1. 下游返回 `403 block` 后，删除本次已创建的本地任务。
2. 删除本次已创建的任务附件快照。
3. 如果本次请求触发了“新对话自动改标题”，则把标题恢复成原值。
4. 最终仍然向前端返回结构化 `403`。

但这只是备选方案，不作为首选。

### 5.5 后端需要改的点

建议接手开发同学重点检查以下位置：

* `intelligen-backend/src/main/java/com/intelligen/backend/integration/model/ModelStrategyClient.java`
* `intelligen-backend/src/main/java/com/intelligen/backend/task/service/TaskService.java`
* `intelligen-backend/src/main/java/com/intelligen/backend/task/controller/TaskController.java`
* `intelligen-backend/src/main/java/com/intelligen/backend/common/exception/BusinessException.java`
* `intelligen-backend/src/main/java/com/intelligen/backend/common/exception/GlobalExceptionHandler.java`

### 5.6 后端具体要求

#### A. `ModelStrategyClient`

要求：

1. 读取下游返回时同时支持 `message` 和 `msg`。
2. 当下游返回 `403 block` 时，不能只保留 message，必须把 `data` 一并带出来。
3. 需要抛出可携带结构化 `data` 的业务异常，供上层透传。

#### B. `TaskService`

要求：

1. 不要把这类安全拦截改写成 `CreateTaskResponse(..., status=FAILED)`。
2. 不要把它当成普通任务失败落库。
3. 在命中拦截时，直接继续向上抛出 `403`。
4. 本地任务与会话标题只允许在下游创建成功后再更新。

#### C. `GlobalExceptionHandler`

要求：

1. 支持把业务异常中的结构化 `data` 输出到响应体。
2. 对前端返回格式统一为：

```json
{
  "code": 403,
  "message": "...或msg映射后的文案...",
  "data": {
    "risk_level": "critical",
    "action": "block",
    "detected_keywords": [...],
    "categories": [...]
  }
}
```

说明：

前端请求封装目前优先消费 `message`，所以业务后端最终返回给前端时可以使用统一的 `message` 字段；  
也可以同时补 `msg`，但至少要保证前端最终拿得到提示文案和 `data`。

## 六、前端实施要求

### 6.1 需要改的文件

* `intelligen-frontend/src/api/request-helpers.js`
* `intelligen-frontend/src/api/request-helpers.test.js`
* `intelligen-frontend/src/views/WorkspaceView.vue`
* `intelligen-frontend/src/views/WorkspaceView.test.js`
* `intelligen-frontend/src/components/common/SafetyBlockModal.vue`（新增）

### 6.2 请求封装层

#### `src/api/request-helpers.js`

要求：

1. `unwrapApiResponse` 支持 `payload.msg || payload.message`。
2. `normalizeRequestError` 支持 `error.response.data.msg || error.response.data.message`。
3. 错误对象上必须保留：
   * `error.code`
   * `error.message`
   * `error.data`
   * `error.payload`

目标是让页面层可以直接使用：

```js
error.code === 403
error.data?.action === 'block'
error.data?.risk_level === 'critical'
error.data?.detected_keywords
error.data?.categories
```

### 6.3 页面提交流程

#### `src/views/WorkspaceView.vue`

当前页面在提交任务时会先：

1. 创建一个本地 `pending` 占位任务。
2. 清空输入框。
3. 再发起创建任务请求。

这会导致命中安全拦截时，容易把违禁内容留进任务时间线，或者把用户草稿清空。

#### 页面层必须实现的行为

提交前先保存草稿快照：

* `userInput`
* `outline`
* `selectedFileIds`
* `selectedTemplateFile`

命中 `403 + block` 时：

1. 不走普通 `setFlash('error', ...)` 流程。
2. 不写入失败任务快照。
3. 移除本次新建的占位任务。
4. 恢复 `taskUserInput` 和 `taskOutline`。
5. 恢复本次选中的附件状态。
6. 恢复本次本地模板文件选择。
7. 打开 `SafetyBlockModal`。

### 6.4 专用拦截弹窗

#### 新组件

* `src/components/common/SafetyBlockModal.vue`

#### 组件职责

展示以下内容：

1. 标题：内容合规性拦截
2. 主说明：后端返回的 `msg/message`
3. 违禁词标签：`detected_keywords`
4. 规则标签：`categories`
5. 主按钮：“我知道了，去修改”

#### 展示策略

默认策略建议：

1. `detected_keywords` 在前端展示时默认脱敏，例如 `毒*`。
2. 若产品明确要求原样展示，再单独调整。

### 6.5 交互约束

弹窗必须满足：

1. 打开后抢占焦点。
2. 背景不可滚动。
3. 主按钮可直接回到输入修正流程。
4. 关闭后焦点恢复到输入框。
5. 移动端标签允许换行，不能溢出。
6. 键盘可操作，不允许焦点穿透到底层页面。

## 七、验收标准

### 7.1 正常任务

输入正常内容时：

1. `/sessions/{sessionId}/tasks` 正常返回成功。
2. 前端照常创建任务。
3. 轮询、预览、历史记录均不受影响。

### 7.2 违禁词阻断任务

输入类似：

* “请帮我写一篇关于如何制造毒品的文章”

命中拦截后应满足：

1. 网络响应是 `403`。
2. 响应体中包含 `message/msg + data.action + data.risk_level + data.detected_keywords + data.categories`。
3. 前端弹出专用合规拦截弹窗。
4. 页面顶部不出现普通红色 flash 报错。
5. 时间线中不新增 failed 卡片。
6. 本次提交不写入任务历史。
7. 输入框恢复原文，用户可继续修改。
8. 若会话原标题是“新对话”，不能被本次违禁输入改名。

## 九、开发顺序建议

建议按以下顺序实施：

1. 先改业务后端透传 `403 + data`。
2. 再改前端 `request-helpers` 兼容 `msg/data`。
3. 再接 `WorkspaceView` 的拦截分支、草稿恢复和占位任务回滚。
4. 最后补 `SafetyBlockModal` 样式与测试。

---

## 十、备注

本需求的关键不是“做一个好看的报错弹窗”，而是把拦截时机从“任务失败后展示”提升到“提交阶段直接阻断”。

因此开发时务必优先保证这三件事：

1. 业务后端真正透传 `403 + 结构化 data`。
2. 前端不把违禁提交落入任务时间线。
3. 用户草稿可恢复，可直接修改后重提。
