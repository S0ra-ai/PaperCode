Development Workflow

开发、验证和文档同步

每个功能都按“代码边界、用户入口、运行事实、监控展示、测试、文档和 changelog”闭环处理。

分支与版本

事项规则
开发分支从 develop 开 feature/<name> 或 fix/<name>。
版本开发态使用 x.y.z.n-dev；pre-release/release 流程才移除 dev 后缀。
changelogroot 只保留当前活跃版本，历史条目进入 docs/changelog/v0/ 归档。
推送节奏完成一个小功能并通过针对性验证后推送一次。

修改闭环

1. 定边界先判断改动属于 TUI、Paper Core、模型路由、Preview、research-tools、schema、文档还是测试。
2. 改代码优先沿用现有模块和类型。新增领域事实放 Paper Core；新增用户入口放 TUI route 或 workbench util。
3. 写事实PaperRun 新能力必须落到 artifact、diagnostics、event、snapshot 或 controller 中，不能只在 UI 中临时计算。
4. 展示TUI 和 Web Monitor 读取同一份 snapshot；Preview 只读，不能直接写 run 状态。
5. 验证根据风险选择单测、typecheck、preview test、benchmark、browser smoke 和 changelog/readme 检查。

文档同步

  • 用户入口、命令、模型配置或安装流程变更时，同步根目录 README.md。
  • 架构、流程、关键函数、测试策略或修改路径变更时，同步 docs/development/。
  • 内部维护和 release 规则变更时，同步 docs/internal/README.md。
  • 每个版本只在 root CHANGELOG 保留当前活跃条目，正文按 colon DSL 分组。
