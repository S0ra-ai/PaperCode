PaperCode 开发手册

这是一套面向维护者的多页 HTML 手册。结构参考成熟 ReadTheDocs 文档站：左侧分组导航、正文按任务链路展开、右侧提供本页目录。

手册主线是开发，同时保留一条完整使用指南。维护者应先用真实 TUI 跑通产品路径，再按产品链路定位模块，同步状态、接口、TUI、Preview、导出和测试。

中文优先 PaperRun-first 开发态 0.13.x MPL-2.0

阅读路线

1. 开发指南按产品链路判断改动归属，定位状态事实、入口层、验证层和质量调优点。 2. 架构说明 TUI、Paper Core、HTTP API、Preview、research tools、schemas 和 run storage 的边界。 3. PaperRun 流程解释 intake、stage graph、artifact、ledger、diagnostics、controller 和 SSE 事件。 4. 关键函数索引按真实调用链定位 create、orchestrator、writing、experiment runner、Preview 和模型路由。 5. 接口与数据契约集中说明 HTTP API、事件、artifact schema、Preview snapshot 和 export manifest 的稳定边界。 6. 修改手册新增 stage、artifact、TUI 页面、Preview 字段、模型策略和测试时的文件清单。 使用指南按使用参数、运行模式、输入材料、质量调优、实时监控和恢复导出组织完整产品路径。

文档写法基准

开发手册参考 ReadTheDocs 的信息组织方式：先给入口和参数，再解释模式、输入、输出、调优、实时状态和排障。区别是本文档主线不是用户教程，而是维护者如何改代码、验证链路和判断质量边界。

定位 使用指南保留完整产品路径，方便维护者复现用户行为；开发手册负责拆代码、拆状态、拆接口、拆测试。任何页面都应该能回答“改哪里、为什么、怎么验收”。
参数 说明一个功能受哪些配置、状态、schema、环境和模型策略影响。
模式 说明主题到论文、材料到论文、代码到论文等不同运行链路的开发差异。
输入 列清 TUI、HTTP API、artifact、source ledger、环境探测和外部工具入口。
输出 写明 TUI、Preview、export bundle、diagnostics、报告和测试证据如何落盘。
调优 覆盖论文质量、格式、实验复现、模型路由、性能和可恢复性。
排障 把常见错误映射到代码路径、日志路径、检查脚本和可执行修复步骤。

开发文档粒度

每个开发页都要能直接落到代码。只写“系统有某能力”不够；必须写清该能力的状态来源、调用链、关键函数、失败边界、测试命令和相邻页面。

必须回答的问题页面中的写法示例落点
状态从哪里来列出 run fact、artifact、model inventory、snapshot 或 diagnostics。PaperRun、PaperModelInventory、PreviewSnapshot.v1
代码从哪里进给出入口函数、handler、领域函数和渲染函数。submitPaperWorkbenchPrompt -> createPaperRun -> composeDraftPaper
要改哪些文件按 TUI、HTTP、Paper Core、artifact、Preview、测试、文档列清文件。routes/paper-models.tsx、model-inventory.ts、paper/run.ts
失败怎么呈现写明 blocked diagnostic、pause question、gate failure、tool diagnostic 或只读拒绝。无模型、无真实来源、实验缺 baseline、PDF 头校验失败。
怎么验收给出最小测试、typecheck、live benchmark、browser smoke 或文档检查命令。check-development-docs.ps1、live-paper-quality-benchmark.ts

手册结构

分组页面用途
入门总览、使用指南、开发指南、开发工作流让维护者先跑通产品，再明确分支、版本、验证和提交约束。
架构架构、模块地图、关键函数索引、接口与数据契约说明代码如何分层、关键函数在哪里、跨模块修改从哪里开始，以及运行数据如何在模块间传递。
运行时PaperRun、论文生成、实验执行、Preview 与导出解释状态机、写作链路、代码实验、实时监控和 final gate。
工作台TUI 与模型、Agent / MCP / Skills、测试与维护、修改手册覆盖用户界面、模型路由、能力包、回归测试和常见改动配方。

维护者任务卡

遇到问题时不要从文件名猜起，先按任务卡进入对应页面，再回到代码。

论文质量不够看 DraftPaper 章节策略、References 规则、中国计算机学报格式、final/forced draft 边界。 代码实验没跑通看协议生成、host/container 执行、GPU/编译器探测、terminal trace 和 ResultReport。 模型工作台问题看 provider 注册、候选池、可用模型、主/备用决策模型和阶段路由。 Web Monitor 或导出异常看 SSE snapshot、只读保护、gate、manifest、PDF/DOCX 文件头和浏览器 smoke。 不知道从哪个函数改按入口、状态、artifact、Preview/export、测试的顺序定位真实调用链。

系统形态

主入口

中文 TUI 是用户主入口。用户输入主题、代码、论文材料、数据或实验日志后，系统创建可恢复、可审查的 PaperRun。

核心状态

PaperRun 持有 intake、stage graph、events、source ledger、claim ledger、agent tree、diagnostics、preview/export 和 controller。

质量边界

final export 只在 source、claim、citation、license 和 reproduction gate 通过后生成；forced draft 必须显式保留失败项。

运行目录

默认写入 ~/.paper_fucker/runs/<run-id>。用户选择工作区后，才使用工作区内的运行目录。

核心流程

1. TUI 收集主题和材料 2. API 规范化 intake 3. Paper Core 创建 run 4. Agent Team 执行 stage 5. Preview SSE 实时更新 6. Gate 通过后导出 
home.tsx
  -> createPaperRunFromPrompt()
  -> POST /paper/runs
  -> createPaperRun()
  -> createResearchRun()
  -> startPaperResearchRun()
  -> publishPaperRunSnapshot()
  -> previewPaperRun() / exportPaperRun()

维护原则

  • 用户可见体验以 PaperCode 和 PaperRun 为主语；底层包名只在开发文档、路径和代码引用中出现。
  • 模型只能来自用户注册并允许的 provider/model 池；候选模型和可用模型必须分开。
  • 代码型论文必须把本地代码 source range 写入 source ledger，并绑定到 ClaimLedger。
  • 实验型论文必须写入 host/container reproduction 证据；缺失时 final export 阻断。
  • 新增功能要同步 TUI、HTTP API、PaperRun artifact、Preview、测试、README 或开发手册。

What's Next?

  • 要改功能，先读 开发指南 和 模块地图。
  • 要追踪运行状态，读 PaperRun 流程 和 Preview 与导出。
  • 要提升论文质量，读 论文生成链路 和 实验执行链路。
